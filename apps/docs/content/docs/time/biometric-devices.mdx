Heimdallone v2 ingests biometric/time-attendance punches into a **raw staging
table first**, then derives attendance from them. Payroll only ever reads the
**derived** attendance records — never the device directly.

## The flow

<Steps>
<Step>**Device** — a terminal (e.g. a ZKTeco fingerprint/face unit) records punches with a per-employee device user-id (the enrolment slot).</Step>
<Step>**Agent** — a small on-site agent (Raspberry Pi) polls the device and POSTs new punches to the v2 ingest endpoint, authenticated by a hashed device API key.</Step>
<Step>**Raw staging** — each punch lands in `attendance_punch` with its raw timestamp and payload preserved, deduped by an idempotency key.</Step>
<Step>**Processor** — maps each punch to an employee, builds attendance events (clock-in/out), and recalculates the daily attendance record (applying the workweek/weekend classifier and shift rules).</Step>
<Step>**Payroll** — reads only the derived, approved attendance records.</Step>
</Steps>

<Callout type="warn" title="Raw is never overwritten; payroll is never written by the device">
  Raw punches are preserved for audit. Attendance is *derived* from them. The
  device sync never writes payroll directly.
</Callout>

## Employee matching

Punches are matched to employees by **device user-id (the enrolment slot)** via the
device→employee map, never by name. A punch that can't be matched is **not dropped**
— it goes to the **unmatched review queue** (an attendance exception) for HR to link,
after which it reprocesses.

<Callout title="Stable id, not the slot index">
  The map keys on the stable enrolment id, not the volatile device serial that
  resets on re-enrolment.
</Callout>

## Timezone

Device clocks are treated as **UTC**; the raw device timestamp is preserved and the
normalized punch time is stored in UTC. The daily attendance date and weekend/holiday
classification use the org timezone (default **America/Guyana**, UTC-4). If a terminal
loses its clock after a power cut it can report local time — agents should correct that
offset before submitting.

## Idempotency

Re-running a sync is safe: each punch has a unique key (`device | device-id |
device-user | second`), so re-sending the same punch is a no-op. This is also what
makes a brief dual-write window at cutover safe.

## Migrating the existing (v1) device

The v1 terminal is brought across as a **backfill + re-point**, reusing this same
pipeline:

- **Backfill** — historical v1 punches are loaded into `attendance_punch` (raw
  preserved, `source = import`, v1 punch id kept in the payload), the device and its
  employee slot-map are pre-seeded, and the processor derives the historical
  attendance records. Run read-only against v1, into a disposable scratch DB only.
- **Re-point** — the on-site agent is pointed at the v2 ingest endpoint (a new device
  registration + API key). The device's actual model is detected over the protocol —
  the stored label is cosmetic; the vendor (e.g. ZKTeco) selects the adapter.

The existing Gist auto-update mechanism is reused. The on-site agent already pulls
its sync script from a public GitHub Gist every few minutes (syntax-check →
hot-swap → restart), so no on-site visit is needed to re-point it. **The Gist
carries code only. Secrets stay in the agent's local `.env`.** At cutover, replace
the Gist script with the v2-native script and update the agent's `.env` with the v2
device ID and ingest key — never put the API key or any device secret in the Gist
or the repo.

<Callout type="warn" title="Cutover steps (operator)">
  1. Log in to Heimdallone v2 as platform owner.
  2. Register the ZKTeco terminal in v2 (vendor `zkteco`, mode `api_ingest`).
  3. Copy the generated v2 device ID.
  4. Copy the one-time ingest API key.
  5. Update the agent `.env`: API URL, device ID, ingest key.
  6. Replace the Gist sync-script content with the v2-native script.
  7. Wait up to 5 minutes (auto-update) or restart the bridge service.
  8. Confirm punches arrive in v2.
  9. Check the unmatched-punch / exception report.
  10. Confirm attendance recalculation and payroll reconciliation stay clean.

  Rollback: keep a copy of the v1 script before replacing the Gist; if v2 sync
  fails, restore the v1 script in the Gist and restart the bridge. If multiple
  unrelated agents share the Gist, publish a new one and point the agent at it.
</Callout>

<Callout title="What to verify after cutover">
  Punch counts match, no unmatched punches remain, attendance records are day-typed
  (weekday/Saturday/Sunday/holiday) correctly, and payroll reconciliation stays
  green. Confirm the agent's last successful sync and that the device clock is on time.
</Callout>
